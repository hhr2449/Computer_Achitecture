## 实验一：测量 L1 DCache 和 L2 Cache 的大小

### 访存序列

设取点的数组范围为m字节，步长为l字节。首先在该范围内选取字节偏移为 $0,l,2l,\ldots$ 的位置，然后随机打乱这些位置，将其连接成一个环。每个位置保存下一个位置的数组下标，最后一个位置指向第一个位置。

测量时反复执行 `index = buffer[index]`。由于下一次访问的位置依赖于当前读取的结果，访问顺序不再是固定间隔的顺序扫描，可以减弱规律性硬件预取的影响，并限制多次读取之间的并行执行。

本实验测试的步长为：
$l\in{32,64,128,256,512}\ \text{B}$

数组范围从 4 KiB 增加到 8192 KiB，并在缓存容量附近设置较密集的采样点。其中，L2 附近的测试点包括 1536、1792、2048、2304、2560、3072、3584 和 4096 KiB。

**实验结果与分析**

实验结果如下图所示。横轴为取点的数组范围，单位为 KiB；纵轴为每次访问的平均耗时，单位为 ns；不同曲线对应不同步长。

![image-20261029003923133](https://raw.githubusercontent.com/hhr2449/pictureBed/main/img/image-20261029003923133.png)

由图可以发现，当array size增加，大小超出 Cache 的大小的时候，由于 Cache Miss，出现了比较明显的访问延迟增加。其中有两个比较明显的台阶

当数组范围不超过 48 KiB 时，平均访问时间基本保持在 3 ns 左右。增大到 64 KiB 后，访问时间上升到约 7 ns，形成第一个明显的台阶。这说明数组范围超过 L1 DCache 容量后，部分访问需要由 L2 Cache 满足。容量转折与 48 KiB 的 L1 DCache 规格相符。

数组范围从 64 KiB 增加到 1792 KiB 时，平均访问时间基本维持在 7 ns 左右。增大到 2048 KiB 时，访问时间已经上升到约 13.9 ns；随后在 2304、2560 和 3072 KiB 处继续上升。这表明在接近 2 MiB 时，L2 Cache 已经难以继续维持较高的命中率。此处转折点相比于 L2 Cache 容量偏小

### 思考题：为什么 L1 DCache 的测量结果与规格相符，而 L2 Cache 可能表现出容量偏小？

本次实验出现了与题目示例相似的现象：L1 DCache 在 48 KiB 的采样点仍保持较低延迟，到了下一个采样点 64 KiB 才明显上升；而 L2 Cache 在 2048 KiB 的采样点就已经出现明显的延迟上升。测量的结果比实际的 L2 Cache 容量偏小

一个合理的解释是，L1 DCache 专门缓存数据，程序指令由独立的 L1 ICache 缓存；而 L2 Cache 是指令和数据统一缓存，测试数组的数据会与程序指令及其他数据竞争缓存空间。因此，L2 的标称容量不一定能全部用于容纳测试数组，即使数组范围尚未超过标称容量，也可能出现额外的缓存缺失，使测量结果表现为略微偏小。
